Beyond Stars: MTTX To Measure Developers' Responsiveness to Dependency Update and Remediation

How fast do open-source packages update their dependencies and remediate known vulnerable dependencies, over time?

Imranur Rahman, Ranindya Paramitha, Mahzabina Tamanna, Laurie Williams
North Carolina State University
Paper (soon) Code PyPI VS Code Extension Open VSX Extension GitHub Action Container (GHCR) Zenodo (soon) Algorithm Video (soon)

Architecture of MTTX. Numbers give the order of the steps. The resolver resolves each version constraint as of a past date, and the dashed slots show where a new ecosystem plugs in.

Overview

Software composition analysis tools tell you whether a project is out of date or vulnerable now. They do not tell you how the project behaved over time. MTTX fills this gap. It computes two metrics for the direct dependencies of a package in npm, PyPI, or Cargo: Mean Time To Update (MTTU), how long the dependencies stay behind their newest version, and Mean Time To Remediate (MTTR), how long the dependencies keep a known vulnerability after a fix is available.

The tool resolves every version constraint as of a past date, so it never uses data from the future. It can compute the metrics for one time window or at every past release of a package, and it runs in batches over thousands of packages.

Results

Design Goals

  Correctness

Every value is right, and a reader can check it. Constraints resolve as of each past date, MTTR counts a vulnerability only after its fix is published, and optional worksheets list every interval.

  Scalability

A study can analyze thousands of packages over their full histories. Batches run in parallel workers, a cache stores registry data, the OSV index is a lookup in memory, and --resume continues after a crash.

  Extensibility

Researchers can add ecosystems, data sources, and analysis choices. Every resolver implements one PackageResolver protocol, and every analysis choice is a command-line option.

Use MTTX in Your Workflow

MTTU and MTTR show how the maintainers of a package responded to new dependency versions and to fixed vulnerabilities in the past. MTTX brings this evidence to each place where you decide on a dependency: when you select it, while you code, and in CI. The same Tool computes every value, so the numbers agree everywhere.

Compare candidate packages before you add one

The web dashboard on this page compares up to five packages from one ecosystem, with no installation. Our server runs the Tool with deps.dev data and shows a bar chart, a table, and a plain-English Explanation of each value. Per-release mode adds line charts that show how MTTU and MTTR changed at each release.

  1. Go to Try It, pick the ecosystem, and type the names of the candidate packages.
  2. Pick a time window and a mode, and then select Compute.
  3. Read the Explanation under the table, and download the CSV file if you want to keep the values.

See MTTU and MTTR next to each dependency while you code

The MTTX extension shows the MTTU and MTTR of each dependency as an inline hint in package.json, pyproject.toml, and Cargo.toml. The hover gives the time window, the data source, and the Explanation, and a link opens a Comparison of the package with alternatives. The extension runs the Tool on your machine.

The first run installs the Tool in a private Python environment (Python 3.10 or later) and offers to build the OSV index, which MTTR needs. To try the extension at once, open the demo project, which has one manifest of each kind.

Report MTTU and MTTR in CI

The MTTX GitHub Action runs the Tool in the pinned container image. It reports the values; it fails the step only when you set a limit and a value is above it.

Review the dependencies that a pull request adds

# .github/workflows/mttx.yml
on: pull_request
permissions:
  contents: read
  pull-requests: write
jobs:
  dependencies:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - uses: imranur-rahman/mttx-action@v1
        with:
          target: pull-request

Track your own packages each week

# .github/workflows/mttx-weekly.yml
on:
  schedule:
    - cron: "0 6 * * 1"
jobs:
  packages:
    runs-on: ubuntu-latest
    steps:
      - uses: imranur-rahman/mttx-action@v1
        with:
          packages: express, koa
          ecosystem: npm
          max-mttr-days: 30

The weekly job also gives step outputs, a job summary, and badge files for shields.io.

Run the Tool yourself, at scale or exactly again

CLI from PyPI

pip install dependency-update-metrics

# One package, with the OSV index built on the first run
dependency-metrics --ecosystem npm --package express \
  --start-date 2024-01-01 --end-date 2025-12-31 --build-osv

# MTTU and MTTR at every release of a package
dependency-metrics --ecosystem pypi --package requests \
  --start-date 2020-01-01 --end-date 2021-01-01 --per-release

# A batch of packages from a CSV file, in parallel
dependency-metrics --input-csv input.csv --workers 8 --output-dir output

Container image on GHCR

The image pins Python, every dependency, and the patched pip. The -osv- tag holds the OSV index of that date, so a rerun uses the same vulnerability data and downloads none.

docker run --rm -v "$PWD:/data" \
  ghcr.io/imranur-rahman/mttx:0.2.1-osv-2026-10-23@sha256:3d528b998884f985e484b1da0cceb1219930c1d38625e18bb9ed9f69bce5c2eb \
  --ecosystem npm --package express \
  --start-date 2024-01-01 --end-date 2025-12-31 --depsdev --json

More container options

Each command reads the package data from deps.dev (--depsdev), as the web dashboard and the GitHub Action do, so that the values agree. Without --depsdev, the Tool reads the registry of each ecosystem.

Pull the image once, so that later runs start at once:

docker pull ghcr.io/imranur-rahman/mttx:0.2.1-osv-2026-10-23

On Linux, add --user, so that the result files in your folder belong to you and not to root:

docker run --rm --user "$(id -u):$(id -g)" -v "$PWD:/data" \
  ghcr.io/imranur-rahman/mttx:0.2.1-osv-2026-10-23 \
  --ecosystem npm --package express --start-date 2024-01-01 --end-date 2025-12-31 --depsdev

MTTU and MTTR at every release of a package, and a batch of packages from input.csv in the current folder:

docker run --rm -v "$PWD:/data" ghcr.io/imranur-rahman/mttx:0.2.1-osv-2026-10-23 \
  --ecosystem pypi --package requests \
  --start-date 2020-01-01 --end-date 2021-01-01 --per-release --depsdev

docker run --rm -v "$PWD:/data" ghcr.io/imranur-rahman/mttx:0.2.1-osv-2026-10-23 \
  --input-csv /data/input.csv --workers 8 --depsdev

For the vulnerability data of today, use the plain tag. It has no OSV index, so the first run with --build-osv downloads the OSV data and keeps the index in your folder for later runs:

docker run --rm -v "$PWD:/data" ghcr.io/imranur-rahman/mttx:0.2.1 \
  --ecosystem npm --package express --start-date 2024-01-01 --end-date 2025-12-31 --depsdev --build-osv

Print the build date of the OSV index that a run uses:

docker run --rm ghcr.io/imranur-rahman/mttx:0.2.1-osv-2026-10-23 --osv-index-date

The mounted folder keeps the output of each run: the results (for example express_results.json), the log run.log, and the cache cache/cache.db, which a later run reuses. Do not add --build-osv to the -osv- tag; image/README.md gives the reason and all other details.

Cite the image digest for an exact rerun. The README lists all options, ALGORITHM.md describes how the metrics are computed, and TESTING.md maps each test to what it checks.

Who Can Use It

  • Researchers who study technical lag, software supply chains, or maintainer behavior can compute MTTU and MTTR for thousands of packages and get a full time series per package.
  • Developers can compare how promptly candidate libraries keep their own dependencies current and patched.
  • Security teams can run a batch over their portfolio to find the projects that lag behind available fixes.
  • Builders of security metrics, such as the OpenSSF Scorecard, can use MTTU and MTTR as signals of maintenance.
